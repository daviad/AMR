# 仿真巡检 AMR + Flutter 上位机

一套跑通的端到端巡检系统：**Gazebo 仿真机器人 → ROS 2 导航栈 → Flutter App / Web 监控大屏**。地图、定位、导航、巡检、视频、告警五条链路都在同一个工程里闭环，不是零散 demo。

**环境**：WSL2 + Ubuntu 24.04 + ROS 2 Jazzy + Gazebo Sim 8.15（gz-sim8）+ MediaMTX；上位机为 Flutter（Android 模拟器与 Web 已实测，iOS 未验证）。**纯仿真，不涉及真实硬件**。

## 它能做什么

### 地图与定位

- Cartographer 2D 建图：激光 + IMU + 轮式里程计先验，产出 `pgm/yaml` 栅格地图。
- AMCL 在已有地图上定位，发布 `/amcl_pose` 与 `map → odom` 变换。
- App 自绘栅格地图：`CustomPainter` + 可插拔图层（底图 / 路径 / 机器人 / 巡检点 / 目标点），支持双指缩放与拖动。

### 导航与任务

- 地图上点一下即下发目标：App → MQTT `amr/cmd/goal` → `mission_bridge` → Nav2 `NavigateToPose`。
- Nav2 全栈：全局/局部规划、速度平滑、碰撞监控、生命周期管理。
- 巡检点与路线管理：增删改点、编排路线、循环执行；巡检 / 待机 / 充电三态状态机，支持一键回充。

### 视频

- Gazebo 相机原始帧 → GStreamer 编码 → MediaMTX，同时产出 `camera`（主）与 `camera_low`（低码率）两路。
- App 主链路走 **WHEP（WebRTC）**；不通时可在相机页**手动**切到 **RTSP（TCP）** 或 rosbridge JPEG，不是自动降级。
- Web 大屏固定走 **HLS**，避开浏览器 WebRTC 的端口与编解码差异。

### 监控大屏 / App

- 同一个 Flutter 工程，`/dashboard` 是 App 与 Web **共用路由**，不是 Web 专属。
- 大屏布局：地图占 60%，视频 + 状态 + 巡检控制占 40%；顶栏显示 MQTT / ROS 连接状态。

### 告警

- 统一告警通道 `amr/alert`：`ESTOP`、`ILLEGAL_MODE`、`ROUTE_EMPTY`、`LOW_BATTERY`、`DOCK_FAILED`。
- App 与机器人之间用 MQTT 遗嘱消息 `amr/status/app_offline` 感知对端掉线。

## 通信与端口

| 用途 | 协议 / 通道 | 端口 | 说明 |
|---|---|---|---|
| 遥测（机器人 → App） | rosbridge WebSocket | 9090 | `/map` `/scan` `/tf` `/odom` `/plan` `/amcl_pose` 等 |
| 指令（App → 机器人） | MQTT TCP | 1884 | `amr/cmd/*`，QoS 1 + `cmd_id` 幂等 |
| 指令（浏览器大屏） | MQTT WebSocket | 9002 | Web 端专用入口 |
| 视频主链路 | WHEP（HTTP 信令）+ ICE | 8889 / 8189(UDP) | App 默认；8189 不能 `adb reverse` |
| 视频兜底 | RTSP（强制 TCP） | 18554 | 相机页手动切换 |
| Web 视频 | HLS | 18888 | 大屏固定 |

话题与消息模型的**唯一真实定义**在 [`amr_app/packages/amr_contracts`](amr_app/packages/amr_contracts)，App 与仿真端共用。

## 快速开始

仿真端在 WSL 内：

```bash
cd /home/dxw/amr
./amr_start.sh           # 启动全链路（默认仅 install/ 缺失时才编译）
./amr_start.sh --build   # 源码改动后强制 colcon build
./amr_start.sh --video test   # 视频源换 videotestsrc，仍跑全链路
```

Windows 侧（与 WSL 脚本同目录）：

```powershell
.\amr_start_windows.ps1   # 同步 Windows 副本 + 构建/安装 Android App
.\amr_web_start.ps1       # flutter build web + 静态服务，打开 /#/dashboard
```

> **连接地址**：App / 模拟器连仿真端要用 WSL 的**局域网 IP**，不是 `localhost`。Windows 一键脚本 `-AmrHost auto` 默认取 WSL `eth0` IPv4。`adb reverse` 只能转发 TCP，UDP 8189 过不去，所以模拟器视频必须走 LAN IP。

完整步骤、排错与端口占用处理见 [docs/RUNBOOK.md](docs/RUNBOOK.md)（唯一权威运行手册），Windows 细则见 [docs/WINDOWS侧操作手册.md](docs/WINDOWS侧操作手册.md)，大屏见 [docs/WEB大屏操作手册.md](docs/WEB大屏操作手册.md)。

## 技术亮点

完整版见 **[docs/技术亮点.md](docs/技术亮点.md)**（每条：短句 + 为什么这么做 + 代码/文档链接）。

- **端到端闭环**：鼠标点地图到机器人跑到位，中间是 MQTT 指令 + Nav2 Action + 反馈/结果回传，不是脚本串起来的假流程。
- **通信分工明确**：WebSocket 传遥测、MQTT 传指令、WebRTC 传视频，各用各的强项，而不是一条通道全塞。
- **弱网与兜底**：视频自动重连（1/2/4/8/10 s 退避）、健康度分级、主/低码流自动切换；源切换是手动兜底。
- **视频链路**：GStreamer 双路编码 → MediaMTX → App 用 `fvp` 替换 `video_player` 底层做硬解，失败回退软解。
- **ROS 2 工程化**：7 个功能包（description / gazebo / slam / nav / inspection / comm / bringup），SDF 场景 + URDF/Xacro 机器人，多个 bridge 处理 ROS ↔ Gazebo ↔ 上位机消息转换。
- **建图稳定性**：定位到里程计漂移与渲染队列时间戳滞后导致的穿墙/错位，逐项修掉，并留下 A/B 实验记录。

# 去TMD大龄

2025 年 4 月，我在蔚来收到裁员通知。在此之前，我已经在开发岗位深耕十余年，一路从业务开发做到业务线技术负责人，习惯了持续交付、扛住压力、带着团队落地项目。被裁之后，我没有立刻扎进招聘市场，心里冒出一个念头：不如试着创业一次，给自己一个窗口期。我给自己定下一年的期限：试一试跨境电商，若是跑不通，一年之后再重新求职。

真正入局才看清现实。跨境电商远不是页面上看到的选品、上架、拍视频那么简单。它极度依赖启动资金、供应链资源、行业信息差，还要有敢试错、扛亏损的魄力，而这些恰恰是我欠缺的。更重要的是，复盘之后我认清了自己的性格：我擅长把复杂的技术问题拆解、落地、闭环，却不擅长长期和流量、库存、回款、平台规则博弈，并不适合走创业这条路。一年的尝试，以认清边界收尾。

等到重新准备求职，才迎面撞上几层叠加的难关：长达一年的职业空窗、整个互联网行业持续收缩、AI 浪潮对传统开发岗位的挤压，再加上绕不开的年龄门槛。一开始我心里还有坚持，外包、小型公司不在考虑范围内；慢慢降低预期，放开所有限制投递，可大部分岗位要么 hc 冻结，要么只是挂着招聘页面，很少有真正匹配、能给到合适空间的机会。

后来靠着朋友引荐，我以外包身份进入工厂做运维。我由衷感激这份机会。这份工作技术门槛不高，岗位要求中专学历就足够，它不是用来发挥我过往技术积累的舞台，但它实实在在帮我续上社保，托住了我和家庭的基本生活底线。夜班熬人，薪资微薄，可它是我这段低谷期的一块浮板。

但浮板不能当岸。我清楚不能一直停在这里被动维持。趁着运维工作碎片时间相对充裕，我主动拓宽技术边界，系统啃了 Android 原生、KMP、Flutter，每一项都动手完成了可运行的 Demo，重新打磨、更新简历，一次次投递，回音寥寥 —— 不是我做不出 Demo，是市场上对应的岗位本身就在急剧萎缩。

很多个夜晚我会陷入巨大的落差感。从学生时代到职场前期，我一直属于上游梯队的人，习惯了靠技术拿到正向反馈，习惯了自己的方案被认可、项目被顺利交付。曾经引以为傲的工程能力，放到当下的招聘市场里，好像突然失去了定价权。颓废、自我怀疑反复袭来，可现实摆在眼前：当年赶上移动互联网风口赚到的收入，基本都沉淀在了房产上，房贷、家庭的责任压在身上，我根本没有躺平的选项。

我也琢磨过当下火热的大模型赛道。冷静梳理之后，我劝退了自己。纯算法方向门槛太高，不是短时间能切入；看似门槛更低的 Agent、RAG 应用开发，表层上手简单，可真正拉开差距的根基，还是扎实的后端架构、分布式、稳定性功底。在现在的就业环境里，这个赛道同样内卷，年龄带来的劣势并不会消失，盲目冲进去，大概率又是一轮消耗式内耗。

持续焦虑解决不了任何问题。慢慢我开始试着理解当下这个时代的矛盾：程序员供给过剩，AI 重构软件生产方式，岗位需求在快速迭代；企业的用人期待、招聘筛选标准，和从业者的能力结构、生命周期，出现了巨大的错配。我必须学着接纳这个客观现实，不再困在 “为什么曾经优秀，现在没人要” 的执念里。

先稳住当下，再寻找长期可以扎根的方向，是我给自己定下的节奏。工厂运维这份工作虽然平淡琐碎，还有夜班，却给了我难得的自主时间。我不想把这段空档期白白耗在刷招聘、反复自我内耗里，我需要找一条能长期深耕、有厚重技术纵深的路。

机缘巧合下，我把目光投向机器人产业。深入调研之后我知道，这个赛道同样不轻松，概念满天飞、资本泡沫此起彼伏，很多方案停留在演示 Demo 阶段，产业化落地还有大量卡点没有突破。但不可否认，机器人是确定性很强的长线赛道，未来一定会迎来爆发。它是一个庞大的交叉学科领域，岗位谱系丰富，而我可以从熟悉的软件开发作为切入点，瞄准机器人软件、系统集成这个方向沉下去。

对比做了十几年的 App 开发，机器人软件是另一种完全不同的技术语境。面向 C 端的 App，需求迭代飞快，产品思路五花八门，千人千面，很多优化是为了业务体验妥协；机器人软件的业务需求相对稳定，可底层的技术复杂度要深得多。高频实时消息调度、软硬协同、资源调度、榨干嵌入式硬件的极限性能、Linux 内核机制、实时性保障、时序同步、故障兜底…… 这些内容，每一块都可以往深处钻研。

做移动端 App 这些年，我一直有种感受：现在消费端手机硬件性能严重溢出，绝大多数所谓的性能优化，本质上只是遵守基础工程常识 —— 耗时操作丢到子线程、规避主线阻塞，很少有真正触碰硬件极限、操作系统底层的硬核场景。我也明白，不少技术赛道走到后期，大部分人终究还是写业务，深度有限，靠技术暴富本身就是小概率事件。可即便如此，与其陷在无尽的情绪消耗里，不如找一件有技术纵深的事踏实去做，帮自己平稳渡过这段艰难的转型期。

我也清醒地认清一件事：哪怕机器人赛道相对互联网，对年龄包容度更高，也不代表我埋头学习就一定能拿到对口 offer。如果抱着 “学完必须找到工作” 的目标，沉重的期待只会压垮自己，并不现实。所以我调整了心态：它首先可以是一份热爱，一个长久的爱好。作为 80 后男生，谁小时候没有被《无敌三四郎》打动过，心底藏着一个拥有属于自己机器人的梦想？

只看书、看教程的学习是悬空的，必须落地做实物。一方面动手实践，才能检验理解是否到位，把零散知识点串成体系；另一方面，完整的项目作品集，也是留给未来的一张门票，万一遇到合适的机会，这就是我重新回到技术主战场的底气。

有意思的是，梳理方案时我发现，机器人产品链条里，恰恰也需要配套的上位机、移动端控制 App—— 兜兜转转，我十几年的 App 开发经验没有作废，反而可以成为我的差异化优势。我的路线也清晰起来：先用老本行把配套控制 App 做扎实，接着在仿真环境里完成机器人控制、导航、感知相关的软件开发验证，最后再逐步对接实体硬件，从虚拟走向实物，同时服务器端也可以补充过来，补上鉴权，认证，云端

业务逻辑，这样就是一个完整的系统。

我很庆幸生在有 AI 的时代。它极大降低了试错门槛，拉高了我的学习效率，很多一闪而过的想法，可以快速转化成可运行的原型，给了我持续往前推进的信心。现在我的模式也在转变：基础学习阶段我坚持手写代码，吃透原理；进入正式工程搭建的时候，我更多是指挥 AI 产出，我负责定义需求、划定边界、评审方案、验证结果、排查坑点。

我慢慢意识到，这恰恰是我们这类有多年工程沉淀的人，最大的优势。年轻人精力旺盛、学习速度快、可以长时间高强度写代码，有他们的节奏和人生规划；而我们的核心价值，不在于比谁敲键盘更快，而在于拆解复杂问题、评估方案风险、预判落地隐患、复盘迭代、把控整体链路的能力。我始终不认同单纯用年龄标签筛选开发者的做法，但我看懂了当下社会的筛选逻辑，选择接纳，不再和规则对抗，转而放大自己不可替代的长处。

我的核心竞争力从来没有消失：十几年一线落地经验、项目复盘能力、问题拆解与闭环能力、带团队交付的经验，还有稳定、长期主义的做事心态。我一直相信，我的思维、分析、解决问题的底子是优等的，只是这份能力，和短期市场里的赚钱机会，从来不是充分必要关系。

去他的大龄。我还没有满四十，距离退休还有二十多年的职业生涯，远没到画上句号的时候。
                                                                          

AI 可以生成代码、加速开发流程，但它依旧需要人来定义目标、把控方向、甄别对错、推动落地。就算有 AI 加持，我们大多数人依然是执行者，不是Boss；只是我们的角色，更偏向于技术负责人、方案把关人。

AI 能够颠覆很多软件行业的生产方式，却改变不了物理世界的客观规律，突破不了硬件的物理极限，更替代不了人对风险、成本、落地可行性的权衡和判断。

我不求一步翻身，只求稳步向前。如果之后能遇到合适的岗位，自然是幸事；就算暂时没有，沉下心打磨相关的作品，深耕底层技术，本身也是在丰富自己。至少能减少内耗，不焦虑。
