## 0. 结论摘要

1. **加后脚轮无效。** 后脚轮（对称布局、摩擦取 0）与现状几乎无差：180° 车体实转/odom 从 **1.1309 → 1.1286**（−0.2%），360° 从 **1.1344 → 1.1343**（−0.01%）。**按"效果更好才保留"的要求，后脚轮不加入 URDF，仅作为一次性验证保留在本文档与脚本里。**
2. **主因确实是脚轮摩擦，但方向与最初假设相反。** 把前脚轮摩擦从 0 提到 **0.02**，比值从 **1.131/1.134 变成 0.969/0.977** —— 误差幅度从 odom 少报 ~13% 降到多报 2–3%，回到 1.0x 附近。也就是说：**mu=0（完全无摩擦）才是造成 13% 系统误差的那个配置**，而不是"摩擦越大越滑"。
3. **轮距/轮半径是对的。** `wheel_separation=0.33`（URDF ±0.165）、`wheel_radius=0.06`（URDF r=0.06）；直线标定 odom/truth = **1.0002 / 1.0001 / 0.9994**（三组均 ≤0.06%），说明有效滚动半径与 0.06 一致，几何不是误差来源。
4. **贴地确实是 URDF/TF 的真错误，不是 RViz 错觉。** 修正前 `odom->base_link` 的 z 恒为 0，而 URDF 里 `base_link` 离地 0.08 m，于是 RViz 里整车被画低 8 cm（轮心落到 −0.02、轮底 −0.08，正好"在地平线以下"）。已新增 `base_footprint`（落地面 z=0）并把 odom 子帧、Nav2 的 base frame 全部切过去；`spawn z` 由 0.13 改为 0.01。
5. **修复后最小导航复验 2/2 SUCCEEDED**，终点误差 0.092 m / 0.017 m；建图链路不受影响（cartographer 用的是 `imu_link` 与 `odom`，不含 base frame）。

## 1. 问题、假设与判据

### 1.1 现象

- 原地自旋时，`/odom` 报 180°，车体实际转了约 203°（真值）；360° 同理，实转 408–450°。即 **odom 系统性少报约 11%–13%**。
  - 注意方向：昨天的说法是"odom 多报约 20°"，实测是 **车体多转 20–23°、odom 少报**。二者对误差的累积效果一致，方向描述以本篇为准。
- 该误差与指令跟踪误差是两件事：`odom` 由轮关节角推得（`/odom` 与 `wheel_deg` 在 10 段里完全相等），因此拆成两个量：
  - **真值/odom = 每单位轮子转动对应多少车体转动**（纯"轮→车"增益，本篇主指标）；
  - **odom/cmd = 轮子实际转了多少 / 指令转多少**（接触滑移，波动大，只做参考）。

### 1.2 假设

| 编号 | 假设 | 若成立，预期 |
|---|---|---|
| H1 | 单前脚轮的回转阻力导致驱动轮打滑，是主因 | 把脚轮摩擦降到 ≈0（C）→ 比值回到 1.0x |
| H2 | 后脚轮能"顶住"车体，抑制过转 | 加后脚轮（B）→ 比值明显下降（如 1.11 → 1.05 左右） |
| H3 | 误差来自轮距/轮半径参数或差速模型 | 三组都差不多 → 与 caster 无关 |

### 1.3 判定口径（复现时必须按这里的定义算）

| 项目 | 定义 |
|---|---|
| 组别 | A：单前 caster，mu=0；B：前+后 caster，mu 均 0；C：单前 caster，mu=0.02 |
| 动作 | 原地 180° ×5（3 正 + 2 负）、原地 360° ×5（3 正 + 2 负），`/cmd_vel` 角速度 0.4 rad/s；每段之后停 2.5 s 结算 |
| 采样 | 20 Hz 连续采 `/odom`、`map->base_link` TF、`/gz_truth` 三路 yaw，逐帧解缠后累加（**不要用端点值**，见 §11.1） |
| 主指标 | `truth/odom` = 段内真值转过角 / 段内 odom 转过角；正负向取绝对值后合并统计（n=5） |
| 辅助指标 | `amcl/truth`（AMCL 相对真值的偏差）、`odom/cmd`（轮子相对指令）、直线段 `odom/truth`（轮半径一致性） |
| 有效段 | 段内 `min(scan)` ≥ 0.75 m（不撞墙）；`odom/cmd` 在 1.00–1.19（轮子确实在转）。**整轮作废的条件**：栈刚启动、RTF 明显 <1 时用墙钟计时会算错仿真时长（C 组 23:06 那次即因此作废重跑） |
| 通过标准 | C ≈ 1.0x（\|误差\| ≤5%）→ H1 成立；B 把 1.13 压到 ≤1.05 → H2 有效；三组无差异 → H3 成立 |

## 4. 判定过程

| 用户判据 | 实测 | 结论 |
|---|---|---|
| C 若回到 1.0x 附近 → 主因为摩擦 | C = 0.9685 / 0.9771（\|误差\| 2.3–3.1%） | **成立**：脚轮摩擦是主因 |
| B 若只把 1.11 压到 1.05 左右 → 双 caster 是缓解不是根治 | B = 1.1286 / 1.1343，几乎没动（−0.2% / −0.01%） | **比"缓解"更弱：完全无效** → 不加后脚轮 |
| 三组若都差不多 → 问题在轮距/半径/打滑模型 | 三组差异巨大（1.13 vs 0.97），且直线标定 1.000 | **不成立** |

补充解释（为什么 mu 越小反而越差）：原地旋转时，两个驱动轮的接地点既要"滚动"又要绕车体中心切向位移，接触滑移由脚轮提供的横向反力部分"抵消"。mu=0 时脚轮对地面完全无横向约束，车体因此多转 13%；mu 从 0 到 0.02 这一小步就能把多转量抵消到只剩反向 2–3%，说明该误差对脚轮接触摩擦极其敏感。

**残余 2–3% 的处理建议**：可做一次小扫点（0.005 / 0.010 / 0.015 / 0.020 / 0.030 / 0.050）找过零点；本次不做（三组任务已完成，且 0.02 已把误差压到导航可接受范围）。**注意：本次不扫点不等于 0.02 是"最优值"，只是"已足够好"。**

## 6. URDF 贴地问题

### 6.1 现象与判定

RViz2 里 Fixed Frame=`map`、Grid 在 z=0，小车看起来整台沉在地面以下。**这确实是 URDF/TF 的真实错误，不是参照系错觉**：

| 证据 | 修正前 | 说明 |
|---|---|---|
| `odom->base_link` 平移 z | **0.00** | 差速插件把 odom 子帧直接放在地面 |
| URDF 里 `base_link` 的几何高度 | 0.08 m | 轮底 −0.08 恰好落在 z=0 |
| 后果 | `base_link` 画在 0、轮心画在 −0.02、轮底 −0.08 | 车体一半、轮子全部在地平线以下 |
| Gazebo 物理高度 | 正确（模型落定后 root 在 0.08） | 所以建图/导航此前能跑，只有 TF 与可视化错 |
| `spawn z` | 0.13（比轮底离地高 5 cm） | 出生后要掉落，容易初始穿模 |

即：**物理是对的、TF 是错的**，两者不一致才是问题根因。

### 6.2 修正方案（Nav2 约定）

- 新增 `base_footprint`（无几何、质量 0.001），作为 URDF 根帧、落在地面；
- 固定关节 `base_footprint -> base_link  z=+0.08`；
- 差速插件 `child_frame_id` 由 `base_link` 改为 `base_footprint`（odom 子帧 z 恒 0）；
- `spawn z` 0.13 → 0.01（根帧已在轮底平面，只需 1 cm 防初始穿模）；
- Nav2 全部 base frame 由 `base_link` 改为 `base_footprint`（7 处，见 §7）。

## 11. 踩过的坑（复现时务必避开）

1. **不要用端点值算转角**：180°/360° 的 yaw 端点会被 wrap 到 (−180, 180]，360° 端点与起点几乎相同，直接相减会得到 0 或 ±359°。必须逐帧解缠累加（`spin_test5.py: unwrap_step`）。
2. **不要用 `/odom` 时间戳计时**：回调排队时 `spin_once` 会一次跳到最后几帧，段内"仿真时长"瞬间跳十几秒，实测每段只转 1.83°。改用墙钟 + RTF≈1。
3. **不要用 `gz model -m amr_robot -p` 取真值**：当前 gz 服务 80% 概率 5 s 超时，一轮能拖到 15 min。改用已桥接的 `/gz_truth`（`/world/indoor/dynamic_pose/info`）。
4. **静止时 `/gz_truth` 不发布**：脚本必须先小幅运动（0.25 rad/s × 0.4 s）唤醒，再开始测量，否则 `truth_*` 全 0。
5. **栈刚启动时 RTF 可能 <0.5**：此时用墙钟计时会导致整轮作废（C 组 23:06 那轮的 `odom/cmd` 掉到 0.11–1.05）。等 `Managed nodes are active` 再多等 30 s。
6. **正负方向要合并统计**：`cmd_deg` 带符号，按 `cmd_deg==180` 过滤只会剩下 3 条正向记录（这就是 JSON 里 `summary.n=3` 的来源）；本篇一律用 `abs(cmd_deg)` 合并 5 条。
7. **PowerShell 里不要内联多行 python/bash**：引号/`$()`/管道会被吞掉，一律写 `.py`/`.sh` 文件再 `cp` 进 WSL 执行。

## 12. 后续建议

1. **脚轮摩擦小扫点**：0.005 / 0.010 / 0.015 / 0.020 / 0.030 / 0.050，找 `truth/odom` 过零点，目标 \|误差\| ≤1%。本次只用 0.02 单点，不宜宣称最优。
2. **不改结构**：数据已证明后脚轮无收益；若未来换真实万向轮（swivel+滚轮），昨天的 79% 结论仍适用，需重新评估。
3. **导航侧补偿**：若不想依赖物理参数，可在控制层对原地旋转的 yaw 指令做 0.97 倍缩放，但这只是"用控制掩盖里程计"，优先选物理参数校准。
4. **App/外部接口**：建议统一改用 `base_footprint` 做位姿查询；`base_link` 继续保留（高度 0.08）用于 3D 可视化。
