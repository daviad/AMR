## 0. 结论与最推荐的动作

### 0.1 对五条核心判断的回应

| 判断 | 结论 | 关键依据 |
|---|---|---|
| 1. 现在只是"模块化"，不算"组件化" | **成立** | 单 Flutter package、单 `pubspec.yaml`、全部相对路径 import；测试仅 2 个文件（8 行 + 213 行）；通信客户端被 9 个业务文件直接依赖 |
| 2. 期望"壳工程 + 按需注入模块" | **方向对，但"运行时注入"不可行** | Dart AOT / Flutter Web 不支持运行时加载新代码；只能编译期组装（path 依赖 + entry/flavor + 路由/Provider 注册）。Flutter federated plugin 也不适用（无独立平台实现或独立发布需求） |
| 3. 通信散落、需要统一通道 | **部分成立**：控制面成立，视频不成立 | 15 处 `.subscribe(` 分布在 11 个文件；9 处 `.publishCommand(` 分布在 4 个文件；但最大客户端只有 191 行。视频 812 行自成生命周期（WHEP 协商 / getStats / 码流切换），不应塞进统一队列 |
| 4. 目标特性：易测/易扩/编译快/易协作/SOLID | **大部分成立，但"编译快"不应作为拆包主因** | 拆包会增加 package 数量与 pub 解析；真正收益是测试隔离、依赖单向、变更影响面可控 `[推断]` |
| 5. ROS 侧是否也该这样 | **不该自造抽象，该补契约与边界** | ROS 2 原生已有 topic/service/action、executor、component container、lifecycle、QoS、参数；本项目真正缺的是类型化接口与包边界（见 §4） |

补充判断：**"不少文件很大"在行数上不成立**。App 只有 1 个文件超过 500 行（`video_stream_service.dart` 812 行），全项目 5032 行；ROS 侧最大 434 行。真正的问题不是"文件大"，而是"一个文件里塞了多种传输/多种生命周期"，以及"UI 直接持有 transport"。

### 0.2 最推荐的三个动作

1. **先抽纯 Dart 契约包**：新建 `packages/amr_contracts`，迁入 `core/topic_mapping.dart`、`core/message_models.dart`、`models/command.dart`、`models/robot_status.dart` 与命令状态机；把现有 213 行状态机测试变成可独立执行的测试。这是成本最低、收益最快、可独立验收的一步。
2. **收口两条通道**：App 只保留 `CommandGateway`（MQTT）与 `TelemetryGateway`（rosbridge），把 15 处订阅、9 处发布从 UI/provider 里移走；视频单独抽 `amr_video`，不进网关。
3. **ROS 侧先立契约**：新建 `amr_interfaces`；把 `mission_bridge.py` 从 `amr_comm` 移到 `amr_mission`，把 `cmd_vel_watchdog` 从 `amr_inspection` 移到 `amr_safety`；JSON 只保留在 MQTT 边界。

## 2. A. App 侧：壳工程 + 模块注入

### 2.1 先纠正三个前提

1. **"按需求注入模块"只能是编译期组装。** Dart AOT 与 Flutter Web 都不支持运行时加载新代码。可选手段只有：path 依赖、不同 `main` 入口、`--dart-define` 配置、路由/Provider 注册表、以及 `deferred import`（仍是编译期分片，Web 不支持）`[推断：基于 Dart/Flutter 平台约束，未在本项目验证]`。
2. **不要用 federated plugin。** 它适合"一个能力有多个平台实现且独立发布"（如摄像头插件）。本项目模块是业务页面与业务领域逻辑，没有独立发布需求，federated 会带来 `platform_interface` / `method_channel` 的样板开销。
3. **按 feature 切包，而不是按层切包。** "所有 UI 一个包、所有 domain 一个包"会产生极宽的公共 API，反而更难独立编译；按 feature 切（map/camera/inspection/dashboard），每个包内部再分层，依赖只允许指向 `contracts` / `transport` / `design`。

### 2.2 目标目录树（分两阶段）

```
amr_app/                          # 壳工程：只做装配，不放业务
├── pubspec.yaml                  # path 依赖
├── lib/
│   ├── main.dart                 # bootstrap：配置、日志、Hive、runApp
│   ├── shell/
│   │   ├── app_shell.dart        # MaterialApp + 路由注册
│   │   ├── routes.dart           # route name -> builder
│   │   ├── module_registry.dart  # ModuleDescriptor 列表（可先硬编码）
│   │   └── di.dart               # ProviderScope overrides
│   └── debug/
│       └── channel_debug_page.dart
├── packages/
│   ├── amr_contracts/            # 纯 Dart：topic、信封、错误码、命令状态机
│   ├── amr_transport/            # 纯 Dart：MQTT/rosbridge 适配器 + 两个网关 + fake
│   ├── amr_video/                # Flutter：WHEP/RTSP/HLS session + 健康/码流策略
│   ├── amr_map_engine/           # 可选：map_view + layers（已有良好接口）
│   ├── feature_map/              # 页面与交互（依赖 contracts/transport/map_engine）
│   ├── feature_camera/
│   ├── feature_inspection/
│   └── feature_dashboard/
└── test/                         # 壳级冒烟（路由、装配）
```

第一阶段**只落地前 3 个包**（contracts / transport / video）；`feature_*` 与 `amr_map_engine` 留到模块边界稳定后再拆。

### 2.3 模块边界规则

| 规则 | 内容 |
|---|---|
| 依赖方向 | `feature_* → contracts / transport / design`；`feature_*` 之间 **禁止**互相 import |
| 契约包 | `amr_contracts` 只依赖 Dart SDK，不依赖 Flutter；这样 `dart test` 可独立跑 |
| 传输包 | `amr_transport` 不含 UI、不含 Riverpod；只暴露接口 + 两个适配器 + fake |
| 跨 feature 通信 | 优先走 contracts 中的领域事件类型 + 由壳层注入的接口；**不引入全局 event bus** |
| 公共 API | 每个包只导出 `lib/<pkg>.dart` 一个 barrel，内部实现放 `lib/src/`，控制接口面 |
| 测试 | 纯逻辑包用 `dart test`；UI 包用 `flutter test` + golden；每个包自带 `example/` 或 `test/` fixture |

模块间"靠接口包还是事件总线"：**接口包**。事件总线在单人项目里只会隐藏依赖、让断点难打；只有当"一个事件有 3+ 个互不关心的订阅者"时才考虑，例如告警广播。当前只有 4 个页面，不需要。

### 2.4 壳工程里放什么

| 内容 | 现状 | 目标 |
|---|---|---|
| 路由表 | `app.dart` 硬编码 4 条 | `shell/routes.dart` + 模块提供 `List<RouteSpec>` |
| DI 容器 | `ProviderScope` overrides（Hive box） | 同一机制 + gateway/transport 的 override（测试替身入口） |
| 配置/flavor | `--dart-define AMR_HOST` | `AppConfig`（host、端口、视频源默认、功能开关）；不引入多 flavor |
| 模块注册表 | 无 | 先硬编码列表；仅当需要"按构建裁剪模块"时才做条件注册 |
| 初始化顺序 | `main.dart` 串行 | shell 负责 bootstrap，模块提供 `Future<void> init()`（可选） |
| 横切能力 | 散落 `debugPrint` | 统一 `ChannelEventSink`（见 §3） |

壳工程**不应**出现：任何 topic 字符串、任何 MQTT/rosbridge 调用、任何具体业务状态。

### 2.5 如何做到"单模块可编译 / 可测"

```bash

cd packages/amr_contracts && dart pub get && dart test

# Flutter 模块：独立分析 + 测试
cd packages/amr_video && flutter pub get && flutter analyze && flutter test

# 壳工程整体
cd amr_app && flutter analyze && flutter test
```

独立 `example` app：仅 UI feature 包需要（`packages/feature_camera/example/`），用一个 `MaterialApp` 直接挂载该页面，配合 fake gateway 验证渲染；纯逻辑包不需要 example。

不建议第一批拆 `pages/*`：页面是 UI 变更最频繁的部分，先拆会制造大量跨包改动，收益低于上面三个。

### 2.7 落地顺序

3. `amr_video`；先统一 session 抽象，再合并两个页面的播放实现。
4. 视需要再拆 `feature_*`；如果不打算多入口/多团队，**停在这里即可**。

## 3. B. 统一通道与执行器

### 3.1 先分控制面与数据面

| 类型 | 例子 | 语义 | 是否进统一执行器 |
|---|---|---|---|
| 控制面命令 | 导航目标、取消、模式、急停、回充 | 有 cmd_id、可超时/重试/取消、需要 ACK/Result | **是** |
| 控制面事件 | 电量、模式、告警、巡检状态 | 低频、可缓存最后值、QoS 0 | 是（作为 telemetry 通道） |
| 高频遥测 | `/tf`、`/scan`、`/plan`、`/map` | 高频、只关心最新值、可丢帧 | 是，但用"最新值覆盖"策略 |
| 媒体流 | WHEP / RTSP / HLS | 连续帧、带宽/抖动/解码，协商式连接 | **否**，独立 `amr_video` |

把视频塞进"优先级 + 重试 + 取消"的队列模型是错的：视频没有"重试一次命令"的概念，它的恢复是重建 PeerConnection / 切码流。`VideoStreamManager`（L628-791）已经证明它需要独立生命周期。

### 3.2 最小接口设计（签名级伪代码）

```dart
// amr_contracts
enum ChannelErrorKind { offline, notReady, rejected, timeout, conflict, canceled, protocol, internal }

class CommandSpec {
  final String topic;              // 仅网关内部可见
  final String cmdId;
  final String traceId;
  final Duration ackTimeout;
  final Duration resultTimeout;
  final bool idempotent;           // 只有幂等命令允许重发
}

sealed class CommandUpdate {
  const CommandUpdate();
}
class CommandAccepted extends CommandUpdate { final int latencyMs; }
class CommandProgress extends CommandUpdate { final double? progress; }
class CommandFinished extends CommandUpdate { final bool ok; final ChannelErrorKind? error; }
class CommandFailed extends CommandUpdate { final ChannelErrorKind error; }

class CommandTicket {
  final String cmdId;
  Stream<CommandUpdate> get updates;   // 单向事件流，首帧必为 accepted/failed
  Future<void> cancel();
  String get traceId;
  DeliveryInfo get delivery;           // transport/latency/attempts，供可观测性
}

class DeliveryInfo {
  final String transport;              // mqtt | rosbridge
  final int attempts;
  final int? latencyMs;
  final String traceId;
}

// amr_transport
abstract interface class CommandGateway {
  CommandTicket send(CommandSpec spec);
  Stream<ConnectionState> get connection;
}

abstract interface class TelemetryGateway {
  Stream<T> watch<T>(TopicSpec<T> spec);   // 引用计数订阅
  Stream<ConnectionState> get connection;
}

class TopicSpec<T> {
  final String topic;
  final T Function(Map<String, dynamic>) decode;
  final int queueLength;               // 高频默认 1
  final int? throttleMs;
  final bool lastValue;                // provider 首帧可取缓存
}

// 可插拔 transport（网关内部，业务不可见）
abstract interface class CommandTransport {
  Future<Delivery> publish(String topic, Map<String, dynamic> payload);
  Stream<Map<String, dynamic>> subscribe(String topic, {String? type, int queueLength = 1});
  ChannelCapabilities get capabilities;   // qos/retained/ordered
}
```

要点：业务只看到 `CommandSpec / CommandTicket / Stream<T>`；topic 与 QoS 留在网关/适配器。`DeliveryInfo` 让业务**可选**读取诊断信息，但不需要理解底层。

### 3.3 执行器要管什么

| 职责 | 建议实现 | 不建议 |
|---|---|---|
| 并发模型 | Dart 单 isolate 内串行化命令（`Future` 链 / 单活动命令） | 引入 Isolate 池（无 CPU 密集任务） |
| 队列与优先级 | 单机器人：`safety` 直通（急停/取消），`command` 单槽（新命令拒绝而非排队） | 多级优先级队列、抢占式调度 |
| 背压 | 遥测高频 topic 用 `lastValue + queueLength=1`；命令不排队 | 通用背压框架/流控算法 |
| 生命周期 | 网关随 app 启动，`ref.onDispose` 释放；订阅引用计数 | 每模块独立生命周期管理器 |
| 超时/重试 | 固定三档：ACK 3s、Feedback 2s、Result 120s；只对幂等命令用同 `cmdId` 重发 | 通用指数退避策略表 |
| 取消 | `cancel` 带独立 cmdId + `targetCmdId`，等 Result 终态 | 本地直接丢弃状态 |
| 错误分类 | 把 transport 异常映射到 8 类 `ChannelErrorKind` | 透传原始异常字符串 |
| 日志/追踪 | 每次状态迁移发一条结构化事件：`trace_id / cmd_id / phase / transport / latency_ms` | 各模块各写 `debugPrint` |
| 指标 | 计数器/时延直方图（命令数、超时数、重连数、订阅数） | 接入 Prometheus/OpenTelemetry（当前规模不值） |

### 3.4 业务不关心底层，但不丢可观测性

三个机制即可：

1. **单一事件汇**：所有适配器把原始收发、错误、重连事件写入 `ChannelEventSink`；业务无感，调试页/日志统一消费。
2. **统一 trace**：`CommandSpec` 创建时生成 `traceId`，沿 ACK/Feedback/Result 全链路透传（App 与 ROS 的 `mission_bridge` 都已使用该概念，只是各自生成）。
3. **诊断随结果返回**：`DeliveryInfo` 携带 transport、attempts、latency；UI 只在 debug 面板展示。

### 3.5 与 Riverpod 的关系

| 角色 | 负责 | 不负责 |
|---|---|---|
| `CommandGateway` / `TelemetryGateway` | 连接、订阅引用计数、重连、超时、trace、错误分类 | 缓存业务状态、驱动 UI |
| Riverpod provider | **读模型/缓存**：最后一次电量、当前命令阶段、连接状态；把 Stream 适配成 UI 可 watch 的形态 | 作为事件总线、做重试/队列 |
| 页面 | 只 watch provider、调用 gateway 方法 | 不 import client、不拼 topic |

现状反例：`MissionCommandCenter` 与 `VideoStreamManager` 都持有 `Ref`（L21/L629），导致领域逻辑无法脱离 Riverpod 测试；目标是把 `Ref` 从执行器/会话里拿掉，改由 provider 注入依赖。

### 3.6 单机单机器人场景下的过度设计（明确不要做）

- 多级优先级（3 级以上）、抢占式调度、命令排队深度 > 1。
- 通用"transport 插件注册 + 运行时发现"。
- 多机器人路由/命名空间分配。
- 持久化离线队列、断网重放（当前 MQTT 只有 QoS1，离线重放会引入幂等复杂度）。
- 通用的"重试策略 DSL"。
- 统一指标框架/Prometheus exporter。
- 把视频、地图栅格、TF 全塞进同一个 executor。
- 为了"统一"而抽象出 5 个接口却只有 1 个实现（当前 MQTT/rosbridge 是仅有的 2 个实现，刚好值得）。

## 4. C. ROS 侧对照

### 4.1 ROS 2 已提供的等价物

| App 侧概念 | ROS 2 原生等价 | 说明 |
|---|---|---|
| 通道 / topic | `rclpy` topic + 自定义 msg | 已有类型、QoS、序列化 |
| 请求-响应 | service | 同步短交互 |
| 长任务 + 反馈 + 取消 | action（`NavigateToPose` 已在用） | 本项目导航已经是 action |
| 执行器 | `rclpy.executors.Executor` / callback group | 不需要自造线程池/队列 |
| 模块装配 | launch + `component_container` + `ComposableNode` | 当前全部独立进程，未使用 |
| 生命周期 | `LifecycleNode` | 适合驱动/需要有序启动的节点 |
| 配置 | 参数 + `declare_parameter` | 已在用（`inspection_node` L33-38） |
| 通信隔离/优先级 | QoS（reliability/durability/deadline）+ callback group | 不需要自定义优先级系统 |
| 进程内零拷贝 | intra-process communication | 需要 component 容器才有意义 |
| 壳工程 | `bringup` 包 + launch 参数 | 本项目 `amr_bringup` 已是雏形 |

结论：**ROS 侧"通道 + 执行器"不需要新造**；把"统一通道"映射为"类型化接口 + 统一 QoS/命名约定"，把"执行器"映射为"rclpy executor + 回调分组"，把"壳工程"映射为"bringup 包"。

### 4.2 该做 / 不该做

| 该做 | 不该做 |
|---|---|
| 新建 `amr_interfaces`，定义命令/状态/结果的 msg 或 action | 自造 `Channel`/`Executor` 包装层 |
| JSON 只在 MQTT 边界出现，进入 ROS 后立即变成类型化消息 | 把所有内部话题继续用 `std_msgs/String` |
| 统一命名与 QoS 约定（命令 QoS1、状态 QoS0、map 用 transient_local） | 用自定义优先级队列替代 QoS |
| 用 launch 事件/健康检查替代固定 `TimerAction` 延时 | 为每个节点写生命周期管理器 |
| 把 `mission_bridge` 独立成 `amr_mission` | 为了"组件化"把 Nav2/SLAM 再拆包 |
| 把 `cmd_vel_watchdog` 移到 `amr_safety` | 给 Python 节点套 component container（收益低） `[推断]` |

类型化的现实约束：外部包 `ros-jazzy-mqtt-client` 的 `primitive: true` 路径目前用于 `std_msgs/String`（`amr_comm/config/mqtt_client.yaml` L3-4、L21-48）。若改成自定义 msg，MQTT 桥无法直接做 JSON→类型转换，需要在 `amr_mission` 里增加一个显式适配节点（MQTT String → 内部类型化命令）。**该能力边界 `[未核对]`：未查阅 mqtt_client 源码/文档，只依据现有配置推断。**

折中方案（推荐）：MQTT 侧保持 JSON 字符串；`amr_mission` 作为唯一解析点，向内部发布类型化 msg/action。这样既不丢外部契约，又让 ROS 内部摆脱"字符串协议"。

## 6. E. 风险与建议粒度

### 6.1 组件化的常见反效果

| 反效果 | 触发条件 | 本项目对策 |
|---|---|---|
| 过度抽象 | 1 个实现就抽接口 | 只在已有 2+ 实现时抽（MQTT/rosbridge、WHEP/RTSP/HLS、MapLayer 已满足） |
| 接口爆炸 | 每包导出十几个类型 | 每包一个 barrel，公共 API 控制在 5 个符号内；内部 `src/` |
| 调试变难 | 多层转发、隐式注册 | 统一 `trace_id` + 原始 `transport` 字段 + debug 页面；不用事件总线 |
| 编译反而变慢 | 包数量增加、pub 解析变复杂 | 拆包前记录冷启动/增量编译数据 `[未核对：未测]`；以"单测可独立跑"为验收，不以"更快"为验收 |
| 跨模块重构成本 | 改契约要动多个包 | 契约包先行并配测试；一次提交内完成迁移 |
| 依赖回环 | feature 互相引用 | 在 CI/脚本里检查 `feature_*` 不得依赖其他 `feature_*` |
| 团队协作假象 | 单人项目照搬多团队流程 | 不做 CODEOWNERS 式拆分；按变更频率拆，而不是按组织架构拆 |

### 6.2 在"一个人维护 + 仿真为主"下建议停在什么粒度

- **App**：壳 + 3 个基础包（contracts / transport / video）；`feature_*` **不拆**，页面继续留在 `lib/pages/`，只是不再直接碰 transport。
- **ROS**：10 个包左右（当前 7 + interfaces / mission / safety / video，合并/改名后约 10）；**不启用** component container、不全量 lifecycle 化、不写自定义 executor。
- **判断标准**：如果一次业务改动需要同时修改 3 个以上包，说明边界切错了，应合并；如果某个包 80% 的改动都来自同一页面，说明拆得没必要。
- **停止线**：当项目仍是单人维护、单机器人、无独立发布需求时，不再向"插件化/多租户/多机器人"演进。

## 7. 对比表：现状 vs 目标

| 维度 | 现状 | 目标 | 判断 |
|---|---|---|---|
| 代码组织 | 单 package 按层分目录 | 壳 + contracts/transport/video 三包 | 值得，包数封顶 4 |
| 独立编译/测试 | 否（单 pubspec；2 个测试文件） | 每包可 `dart/flutter test` | 值得，第一步 |
| 模块装配 | `main.dart` 硬编码 + ProviderScope | shell 路由表 + 注册表 + overrides | 小步做，不做插件化 |
| 通信 | UI/provider 直连 client（15 订阅/9 发布） | 两个 gateway + 执行器 | 值得，先泛化现有 center |
| 视频 | 812 行单文件 + 大屏重复实现 | `amr_video` 统一 session | 值得 |
| ROS 契约 | `std_msgs/String` + JSON | `amr_interfaces` 类型化，JSON 仅 MQTT 边界 | 值得，收益最大 |
| ROS 包边界 | 业务桥在 comm、安全在 inspection | mission/safety 独立 | 值得，只动 3 个包 |
| 启动编排 | 固定 `TimerAction` 5–12s | 就绪事件/action server 检测 | 看规模 |
| 进程模型 | 全独立进程 | 保持独立（可选 component） | 不值得改 |
| 多团队协作 | 单人 | 不追求组织级拆分 | 明确不做 |
