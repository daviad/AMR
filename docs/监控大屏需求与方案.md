> 状态：规划文档（本轮不写实现代码、不改既有代码与文档、不跑构建、不启动仿真）

> 核对时间：2026-11-05，核对方式：读代码/配置/历史运行日志 + 只读系统采样

## 0. 摘要

- 现有 Web 大屏只解决了"看地图 / 看相机 / 看状态灯"，**看不到任何"AI 分析结论"与"链路中间量"**：没有话题频率、TF 完整性、位姿误差、控制链各段数值、资源与网络、进程存活、仿真时钟。
- 数据源其实已经天然存在：`/cmd_vel_nav → /cmd_vel_smoothed → /cmd_vel`、`/odom`、`/amcl_pose`、`/tf`、`/scan`、`/map`、`/gz_truth`（Gazebo 真值）、`/clock`、`/video/metrics`、`/client_count`、MQTT `$SYS`、`/proc`、MediaMTX、`~/arm_logs`。**缺的不是数据，是统一采集、降采样、可视化和"可复核证据"。**
- 推荐架构 **B：独立轻量采集器（rclpy + /proc 采样 + WebSocket/HTTP）+ 免构建静态页面（uPlot）**。理由是：任何方案都绕不开 Linux 侧采集器；Flutter Web 做多路实时曲线会掉帧且需要重建；WSL 内没有 Node，免构建方案最省事。
- P0 只做 5 组指标：**位姿误差（估计 vs `/gz_truth`）、关键话题/TF 健康表、控制链四段实测值、视频链路（含已知 0.61 Hz 新内容率）、RTF 与仿真暂停**。
- 最大未知：`/gz_truth` 经 bridge 后 **frame 名丢失、只取 `transforms[0]`**，必须实测确认它确实对应 `amr_robot`，以及 `map` 与 `world` 的坐标对齐方式；否则"误差曲线"会系统性偏移。

## 2. 指标清单（核心）

### 2.0 读表说明

- **采样频率**：写"源频率 → 采集器聚合频率"。采集器不把源频率原样上送，见 §5.3。
- **正常区间**：优先用实测基线（标注来源）；没有基线的写"待实测 + 编号"，不编造数字。
- **异常判据**：默认需要**连续 3 个聚合样本**成立才置告警（去抖），表中不再逐条重复；带"持续 N s"的除外。
- **优先级**：P0 只覆盖"当前已知问题能否被看见"；P1 覆盖长期监控；P2 为增强。
- **采集开销**：相对**单核**的 CPU 占比估算，不是 28 核总占比。

### 3.3 信息密度与可读性权衡

- **三层信息**：L0 顶部 5 个灯（3 秒判断"哪里坏了"）；L1 面板大数字与状态色；L2 点击展开的曲线/表格（排查时使用）。
- **单图 ≤6 条曲线**，超过则拆成 small multiples；禁止双 Y 轴；固定量程（误差 0–1 m、CPU 0–400%），避免自动缩放造成"看起来正常"。
- **数字优先**：关键值字号 28 px、标签 12 px；单位写在标题而非每个刻度；小数位固定（误差 3 位、CPU 0 位、fps 1 位）。
- **历史窗口**：默认 10 min；可切 30 min / 2 min；超过 10 min 用 min/max 包络，避免抽稀丢尖峰。
- **空态**：不仅显示"--"，同时显示"最后消息 3.2 s 前"，让"没数据"和"值为 0"可区分。

| 视频内容率 | <0.3 Hz | 冻结 >2 s |
| `/video/metrics` state | DEGRADED 5 s | OFFLINE |
| HLS 序列 | 3 s 不增 | 10 s 不增 |
| 可用内存 | <5 GiB | <2 GiB |
| `/dev/shm` | >80% | >95% |
| 进程缺失 | — | 任意关键进程 |
| 采集器自身 CPU | >5% 10 s | >10% 10 s |

### 3.5 "分析结论可追溯"（针对原始诉求）

每个面板标题右侧固定一个 **来源徽标**：显示主数据源（如 `/gz_truth + /amcl_pose`）与一个"复制验证命令"按钮（命令来自 §1.5 或指标表）。事件流每条也带 `source` 与 `verify_cmd`。这样任何一条曲线都能在 5 秒内被人工复核，不再出现"AI 说误差 0.9 m 但看不到过程"的情况。

## 4. 实现方案对比

### 4.1 方案 A：扩展现有 Flutter Web 大屏

做法：在 `dashboard_page.dart` 增加监控页/分区，用 Riverpod 新增 provider，通过现有 rosbridge 订阅新话题；资源类指标由新增的 Linux 采集进程发布成 JSON 话题（如 `/amr/obs/snapshot`），Flutter 经 rosbridge 消费。

- 优点：单一大屏、跨端（Android/iOS 可复用）、无新端口、与现有 MQTT/ROS 连接管理一致。
- 代价：仍需 Linux 侧采集器（`/proc` 不可能在浏览器里读）——A 并不是"零后端"；需要图表库或自绘；Flutter Web 在 CanvasKit 下多路 1–5 Hz 曲线 + 地图重绘容易掉帧；任何改动都要在 Windows 拷贝里 `flutter build web`，回归风险落在已经脆弱的地图/视频页。

### 4.2 方案 B：独立采集器 + 独立页面（推荐）

做法：`tools/observer/collector.py` 单进程（rclpy 线程 + asyncio WS/HTTP + 采样线程），输出 `hello/snapshot/delta/event`；前端为**免构建**的 `index.html + app.js + uplot.iife.min.js`（uPlot 约 50 KB），由采集器同端口静态托管。

- 优点：零新增运行时依赖（Python 3.12 + numpy + websockets 已具备，无 Node）；uPlot 绘制 10 万点仍流畅，2 Hz 重绘 CPU 很低；采集与渲染同进程、同源，无 CORS；可在 Linux 侧快速迭代；对现有大屏零侵入（P1 再加一个入口/iframe 即可）。
- 代价：多一个后台进程与端口（8090）；需要写 Python（约 600–900 行）；与 Flutter 端状态不同步（但本方案只读，不影响控制）。

### 4.3 方案 C：现成方案

| 方案 | 能否直接用 | 缺什么 |
|---|---|---|
| rosboard | 可显示话题列表、图像、地图、TF/3D | 无 `/proc`/网络/进程资源；无自定义告警与历史；界面不适合作为固定大屏 |
| Foxglove Studio | 可接 rosbridge，3D/Plot/Diagnostics 强 | 无宿主机 `/proc`、MQTT `$SYS`、HLS 新鲜度；布局手工、较重；适合临时排障 |
| PlotJuggler | 桌面 Qt，适合离线/回放 | 无 Web 大屏、无资源采集；适合 P2 事后分析 |
| rqt_plot / rqt_graph | 桌面点状工具 | 无历史、无告警、无资源 |

结论：C 类只能作为**辅助排障**（TF/3D 用 Foxglove，离线回放用 PlotJuggler），不能满足"固定大屏 + 资源/网络 + 长期监控"。

### 4.4 逐项对比

| 维度 | A 扩展 Flutter | B 独立采集器 + 独立页 | C 现成方案 |
|---|---|---|---|
| 开发量 | 中高（Dart 图表 + provider + 采集器仍要做） | 中（Python 采集 + 单页，无构建） | 低（部署）但定制成本高，且关键指标做不出来 |
| 运行开销 | 高（CanvasKit 多图表重绘 + 地图/视频并存） | 低（2 Hz 重绘，uPlot 增量绘制） | Foxglove 较重；rosboard 中等 |
| 可扩展性 | 中（受 Web 图表性能与 Flutter 重建周期限制） | 高（加面板=加一段 JSON/一个 uPlot） | 低（受插件/面板能力限制） |
| 与 `amr_start.sh` 集成 | 中（Flutter 服务 + 采集器两处） | 低（一行后台启动 + PID/日志 + 一条 verify） | 中（多服务/多端口） |
| 对现有大屏影响 | 高（改页面、需重建、回归风险） | **无**（P0 完全独立；P1 只加入口） | 无 |
| 调试友好度 | 中（DevTools，但数据在 Dart 层） | 高（curl JSON、JSONL、命令按钮、直接改脚本） | 中高（3D/plot 强，资源/通信弱） |
| 跨端复用 | 高 | 低（仅 Web 大屏） | 低 |

### 4.5 推荐：B

1. **A 也必须做 Linux 采集器**，所以"用 Flutter 省一个后端"并不成立；A 相对 B 只多了 Flutter 侧的图表与重建成本。
2. 现有大屏的地图与视频链路仍在修（0:00/黑屏），此时改造同一页面会把"观测工具"和"被观测对象"绑死，排障时容易互相干扰。
3. WSL 内无 Node，B 的免构建静态页反而比 Vite 更稳；uPlot 在 2 Hz 刷新下对 RTF/`/scan` 的影响可忽略。
4. B 的采集器是唯一"知道所有数据源和阈值"的地方，后续 P1/P2 加资源、MQTT、回放都在一个进程内闭环。
5. 如果后续确实需要移动端复用，再让 Android 端读同一个 WS（跨端只读页面），不需要把图表塞回 Flutter。

## 5. 接口与数据结构（方案级）

### 5.1 采集器组成（单进程、三线程）

| 组件 | 职责 | 线程 |
|---|---|---|
| ROS 采样 | rclpy executor，订阅 §2 中 ROS 话题，写入环形缓冲；只读 | 线程 1 |
| 主机采样 | `/proc`、`statvfs`、HTTP m3u8、`$SYS`（P1）、端口探测 | 线程 2（1 Hz 定时） |
| WS/HTTP 服务 | `GET /`（静态页）、`GET /api/snapshot`、`GET /api/health`、`WS /ws` | asyncio 主线程 |
| 聚合器 | 1 Hz 聚合、阈值判定、事件生成、自降级 | 采样线程内 |

后端不发布任何 ROS 消息，不调用任何 action，不写 `~/arm_logs` 之外的路径。

### 5.2 WebSocket 协议（示例 JSON）

连接后先发 `hello`（含序列元数据与"验证命令"）：

```json
{
  "type": "hello",
  "v": 1,
  "session": "20261105-2210",
  "clock": {"sim": 1234.56, "rtf": 1.02, "paused": false},
  "series": [
    {
      "key": "pose_err_e",
      "label": "位姿误差(欧氏)",
      "domain": "sim",
      "unit": "m",
      "color": "#EB5757",
      "thresholds": [0.15, 0.5],
      "precision": 3,
      "source": "/amcl_pose + /gz_truth",
      "verify_cmd": "ros2 topic echo /gz_truth --once"
    }
  ],
  "panels": {"sim": "OK", "loc": "OK", "ctrl": "OK", "video": "WARN", "comm": "OK"}
}
```

周期增量（2 Hz，单帧 ≤30 KB）：

```json
{
  "type": "delta",
  "seq": 43,
  "tw": 1762345678901,
  "ts": 1234.56,
  "rtf": 0.98,
  "v": {"pose_err_e": [0.091], "v_cmd": [0.25], "v_odom": [0.24]},
  "topics": [{"n": "/scan", "hz": 10.03, "age": 0.04, "s": "OK"}],
  "nodes": [{"n": "gz sim", "cpu": 132.0, "rss": 420.0, "alive": true}],
  "events": [
    {"tw": 1762345678800, "lv": "WARN", "src": "video", "code": "HLS_STALE",
     "msg": "media sequence 未增长 3.2 s"}
  ]
}
```

事件（即时推送，不等待聚合）：

```json
{
  "type": "event",
  "tw": 1762345679000,
  "lv": "CRIT",
  "src": "tf",
  "code": "TF_EDGE_LOST",
  "msg": "map->odom 缺失",
  "ctx": {"edge": "map->odom", "age_s": 2.1},
  "verify_cmd": "ros2 run tf2_ros tf2_echo map base_link"
}
```

断线重连：客户端先 `GET /api/snapshot?window=1800&step=1` 拿最近 30 min 降采样历史，再订阅 `/ws`；服务端在缓冲不足时补发 `snapshot` 而非 `delta`，客户端按 `seq` 去重。

### 5.3 采样与降采样

| 数据 | 源频率 | 原始环形缓冲 | 上送/落盘 | 方法 |
|---|---|---|---|---|
| `/odom`、三段 cmd_vel | 50/20 Hz | 最近 20 s（10 Hz） | 5 Hz（火花线）+ 1 Hz（历史） | 每秒取 mean/min/max，保留尖峰 |
| `/tf` 各边 | ~82 Hz | 最近 20 s（10 Hz） | 1 Hz | 只存频率与 age，不存变换矩阵 |
| `/scan` | 10 Hz | 最近 60 s 计数 | 1 Hz | 只计数与时间戳，不读 `ranges` 数组 |
| `/camera/image_raw` | 5 Hz | 最近 20 s 哈希 | 1 Hz 唯一帧计数 | 64×48 灰度 > 阈值即算"新帧" |
| `/video/metrics` | 1 Hz | 最近 30 min | 1 Hz 直通 | 解析 JSON 关键字段 |
| `/proc`、网络、磁盘 | 1 Hz | 最近 30 min | 1 Hz | 直通 |
| 事件 | 事件 | 最近 1000 条 | 全量 | 按 code 去重，保留首次/末次 |

- 历史 30 min、1 Hz、约 30 条序列 ≈ 5.4 万个点，JSON 约 0.5–1 MB，适合一次 `snapshot` 下发。
- 超过 10 min 的窗口一律 min/max 包络绘制，避免"抽稀丢尖峰"。
- WS 帧硬限制 30 KB；超限时只发变化最大的 10 条序列，其余下一帧补。

### 5.4 时间同步（必须严格遵守，否则曲线错位）

| 数据 | 时间域 | 依据 | 图表 x 轴 |
|---|---|---|---|
| 位姿、TF、`/odom`、`/scan`、cmd_vel | **仿真时间** | 节点 `use_sim_time=true`；`header.stamp` 与 `node.get_clock().now()` | x = sim |
| `/video/metrics`、`/video/health` | **墙钟** | gst 节点 `use_sim_time=False`，JSON 里是 `timestamp_ms`（[full_bringup.launch.py#L152-L153](../amr_sim_ws/src/amr_bringup/launch/full_bringup.launch.py#L152-L153)） | x = wall |
| `/amr/alert`、`/amr/cmd/*` | **墙钟** | `_now_ms()` 为 `time.time()`（[mission_bridge.py#L34-L35](../amr_sim_ws/src/amr_comm/scripts/mission_bridge.py#L34-L35)） | x = wall |
| `/proc`、`$SYS`、HLS、MediaMTX | **墙钟** | 宿主机时间 | x = wall |
| 浏览器 | 墙钟 | Windows/WSL 可能有秒级偏差 | **只显示相对时长**，不用绝对时刻做判断 |

- 每个数据点同时记录 `tw`（墙钟毫秒）与 `ts`（仿真秒），`series` 元数据声明 `domain`。
- 不同 `domain` **绝不共用同一 x 轴**；并排小图或"双时间游标"联动，联动按 `seq` 而非按 x 值。
- 仿真暂停：`ts` 停止推进，`tw` 继续；曲线在墙钟轴上留空档，并绘制 `PAUSED` 灰带；暂停期间**抑制所有基于仿真 age 的告警**（否则会误报 TF/scan 超时）。
- 仿真加速（RTF>1）：sim 轴会"跑得比墙钟快"，历史窗口按 sim 时间裁剪；UI 标注"加速中"。连续 RTF>1.2 持续 5 s → WARN。
- HLS/视频一律按墙钟统计，避免 RTF<1 时"看起来视频变慢"的误判。

### 5.5 断线重连、历史与回放

| 阶段 | 历史 | 落盘 | 回放 |
|---|---|---|---|
| P0 | 内存 30 min（1 Hz） | 无 | 无；刷新页面即丢 |
| P1 | 内存 30 min + 事件 1000 条 | 可选 JSONL（1 Hz，写 `~/arm_logs/<ts>/obs/metrics.jsonl`），单文件 50 MB × 4 轮转，保留 7 天 | 无（仅可用文本查看） |
| P2 | 同上，可跨进程恢复 | 同上 | 页面 `?replay=...` 读取 JSONL，播放/拖动/A-B 对比/导出 CSV+PNG |

- 重连策略：1 s → 2 s → 5 s 退避；恢复后补 `snapshot`，曲线连续、无断点；顶部短暂显示"RECONNECTED"。
- 不引入时序数据库（理由见 §7）；JSONL 足够支撑"事后 30 分钟内复看"。

### 5.6 单进程 vs 多进程

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 单进程（推荐） | 一个 PID、一个端口；数据零 IPC；`amr_start.sh` 只加一行 | 采集器崩溃会同时丢页面 | 用启动脚本的"存活检查 + 重启"兜底；P0/P1 足够 |
| 采集与 Web 分离 | 页面不受采样崩溃影响 | 两套生命周期、IPC/序列化复杂 | 仅当采集 CPU 长期 >5% 或需要独立权限时再拆 |

### 5.7 采集自身开销上限与自降级

- 上限：**CPU <3% 单核、RSS <180 MiB、WS 2 Hz/≤30 KB、无子进程**。
- 自监控：采集器每秒读自己的 `/proc/self/stat` 与 `/status`，在上送数据里带 `obs_cpu`/`obs_rss`，页面角标显示。
- 自降级（按顺序）：
  1. 相机哈希 5 Hz → 1 Hz（省 0.5–1%）；
  2. WS 从 2 Hz → 1 Hz；
  3. `/imu`、`/scan` 计数降为 2 s 聚合；
  4. 关闭 `/proc/diskstats` 与日志扫描（P1 项）。
- 恢复条件：连续 60 s CPU <2% 才逐级恢复，避免抖动。
- 验收时必须证明：采集器运行前后 `/scan` 频率变化 <0.5 Hz、RTF 变化 <0.02。

### 5.8 安全与边界

- 默认只监听 `127.0.0.1:8090`（WSL mirrored 下 Windows 浏览器 `localhost:8090` 可达）。
- 如果 WSL 是 NAT 模式，只能监听 WSL IP 并放行 Windows 防火墙；**不要直接绑 0.0.0.0 暴露到局域网**。
- 本版本无鉴权、无写操作、无 ROS 发布；页面只读。

| `amr_sim_ws/src/amr_gazebo/config/mediamtx.yml` | 可选：开启 `api`/`metrics` |
| `amr_app/lib/pages/dashboard_page.dart` | 仅加"监控"入口（改完需同步 Windows 副本并重建 Web 产物） |
| `docs/监控大屏需求与方案.md` | 增补 P1 实测基线与阈值 |

**风险**：改 `amr_start.sh` 可能影响现有启动/停止时序；`mediamtx.yml` 开启 API 会多一个本地端口；Flutter 入口改动需要重建，可能触及正在修复的视频页。缓解：P1 的脚本改动保持"只追加、不改原有顺序"，大屏入口放在最后做。

### 6.3 P2：历史回放 / 告警规则 / 导出

**做什么**

- JSONL 回放页面：拖动时间轴、A/B 两次运行对比（例如改 Cartographer 参数前后）、导出 CSV/PNG。
- 告警规则可配置（阈值、去抖窗口、静音时段），事件流支持按 code/level 过滤。
- 内嵌到大屏（iframe / Flutter `HtmlElementView` 卡片），支持"地图 + 观测"同屏。
- 可选：给 `cmd_vel_watchdog.py` 增加 `/amr/status/watchdog` 计数并映射到 MQTT；给采集器增加 Cartographer 约束分（若 U2 确认有话题）。

**验收**

- 重启采集器后可恢复最近 30 min 曲线；回放能定位到任一次 `goal` 前后 60 s。
- 两次运行对比能同图显示误差/RTF/视频 fps。
- 导出 CSV 字段与页面对得上，PNG 含阈值线与时间范围。

**预计改动文件**：`tools/observer/web/replay.html`、`tools/observer/web/replay.js`、`collector.py`（落盘/读取）、`amr_sim_ws/src/amr_inspection/amr_inspection/cmd_vel_watchdog.py`、`amr_sim_ws/src/amr_comm/config/mqtt_client.yaml`、`amr_app/lib/pages/dashboard_page.dart`。

**风险**：历史数据体积与日志清理策略冲突；回放解析 JSONL 可能拖慢浏览器（需流式读取）；内嵌 iframe 受同源/端口策略影响。

## 7. 明确不做

- 多机器人 / 多仿真实例聚合；车队级调度视图。
- 云端上传、公网访问、远程运维、账号/权限/审计（本版本无鉴权）。
- 长期时序数据库（Prometheus / InfluxDB / TimescaleDB）与告警平台接入。
- 从大屏下发控制或自动调参（页面只读；控制仍走 MQTT 原有链路）。
- 视频录制、回放、目标检测、点云/图像全量存储与可视化。
- 替换 RViz / Foxglove / PlotJuggler；不重复实现 3D 场景交互。
- 移动端布局适配、i18n、主题切换。
- 告警外发（飞书/邮件/短信）。
- 对 SLAM/Nav2 参数的自动 A/B 调整（P2 只做手动对比展示）。

## 8. 风险与坑

| 风险 | 表现 | 规避 |
|---|---|---|
| 仿真时钟暂停 | RTF=0，所有"age 超时"同时误报；曲线在墙钟轴上看似断流 | 先判 `Δsim`；暂停期间抑制 sim-age 告警并显示灰带 |
| RTF<1 或加速 | sim 轴与 wall 轴比例变化，曲线"压缩/拉伸" | 每序列声明 domain；不同 domain 不共用 x 轴；tooltip 同时显示两个时间 |
| rosbridge 的 `TRANSIENT_LOCAL` | `/map` 在采集器晚订阅时为空；大屏能显示地图可能只是订阅时机合适 | 采集器直接 rclpy 订阅 `/map` 时显式 `TRANSIENT_LOCAL + RELIABLE`；不依赖 rosbridge |
| rosbridge 频率限制/节流 | 用 rosbridge 做采集会丢消息、算错频率 | 采集器走原生 DDS；rosbridge 只服务现有大屏 |
| `ros2 topic hz` 自身开销 | 每次执行新建订阅与 CLI 进程，长期跑会污染结果 | 只在人工核对时用；采集器自己计数 |
| Flutter Web 大量实时图表掉帧 | CanvasKit 重绘 + 地图/视频叠加，风扇狂转且曲线卡顿 | 不在 Flutter 里做主监控区；P2 才考虑 iframe 内嵌 |
| `/gz_truth` 不确定性 | frame 名丢失、只取 `transforms[0]`；若 world 里有其他动态实体，取到的可能不是机器人 | U1 先确认；多实体时改用 `gz model -m amr_robot -p`（1 Hz 子进程）兜底，或新增按实体过滤的桥接 |
| map/world 坐标不对齐 | 绝对误差恒定偏移，看起来"一直很差" | 起步静止 5 样本标定 `T_map_world`；未标定时以 Δs 为主 |
| `/amcl_pose` 事件式发布 | 静止时长时间无消息，被误判为"定位挂了" | 用 `/odom` 位移作为前置条件；静止时只显示"上次更新"，不报警 |
| `/scan` 重复发布者 | 重启后残留 ghost node，频率翻倍或数据跳变 | 采集器记录 publisher count；U10 核对；`amr_start.sh` 清理残留 |
| MediaMTX API 未开启 | 拿不到 WHEP 会话/帧率 | U5 确认；P1 显式开启 `api` 或解析日志 |
| `$SYS` 被关或周期过长 | MQTT 指标为 0 或 10 s 才更新 | U7 确认 `sys_interval`；阈值按 10 s 设计，不要求秒级 |
| 相机哈希开销 | 订阅图像会复制 230 KB/帧，极端情况下抢占 CPU | 只取 5 Hz，按需降为 1 Hz；不订阅编码后数据 |
| HLS 0:00 根因未明 | 监控只能"看见断流"，不能自动修复 | P0 明确只做观测；把内容率与序列号作为证据留给后续修复 |
| WSL 网络模式 | NAT 模式下 Windows 打不开 `localhost:8090`，UDP 8189 也可能不通 | 默认 mirrored；文档写明切换 WSL IP + 防火墙的处理 |
| Windows/WSL 时钟偏差 | 浏览器时间与 WSL 墙钟差几秒，绝对时刻对不上 | 只显示相对时长与 age；不做跨主机绝对时间判断 |
| 日志无限增长 | `full_bringup.log` 5.79 MiB/次长跑，长期跑会累积 | P1 监控增长；沿用现有按时间戳分目录与清理策略 |
| 采集器自身故障 | 页面空白，误以为系统挂了 | 顶部显示 OBS 状态；`amr_start.sh` 做存活检查与重启；`/api/health` 供 `verify_all()` 调用 |
